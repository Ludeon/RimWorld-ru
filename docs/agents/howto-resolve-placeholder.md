# Как узнать, что подставляется в плейсхолдер строки

Задача: в строке вида `...{0}...{ИМЯ}...{ИМЯ_подсимвол}...` нужно понять, какие значения
реально могут оказаться на месте плейсхолдера — например, чтобы решить, как согласовать
род/число/падеж в переводе.

Механизм разрешения плейсхолдеров (`GrammarResolverSimple.Formatted`/`TryResolveInner`,
`NamedArgument`) один и тот же для строк из любого источника — и для Keyed-ключей
(`docs/agents/keyed-strings.md`), и для полей дефов, переопределяемых через DefInjected
(`docs/agents/def-injected.md`): в обоих случаях в коде игры в какой-то момент вызывается
`.Formatted(...)` (или `.Translate(...)` с аргументами, который делает то же самое) над
строкой, полученной локализованной. Разница только в том, **как искать место этого вызова**
(шаг 1) — дальше (шаги 2–6) алгоритм одинаковый.

## Шаг 1: найти место вызова `.Formatted(...)` / `.Translate(...)`

- **Если строка — Keyed-ключ** (`<Keyed/*.xml>`): грепом по `.Decompiled/**/*.cs`
  (декомпилированный код игры, см. AGENTS.md) найти `"ИмяКлюча".Translate(`.
- **Если строка — поле дефа** (`<DefInjected/ТипДефа/*.xml>`): по [def-injected.md](def-injected.md)
  определить, к какому дефу и полю относится путь инъекции; затем найти в коде, где это
  поле читается (обычно через свойство класса компонента/воркера, например
  `Props.message`, `def.description`), и посмотреть, вызывается ли на нём `.Formatted(...)`.
  Само поле дефа в C#-классе обычно объявлено как `string` или `TaggedString`.

Если юнкшен `.Decompiled` не настроен — сказать об этом прямо и предложить
`script/setup.ps1`, не гадать по названию ключа/поля.

- Если вызовов несколько — разобрать каждый; разные места вызова могут передавать разные
  типы объектов на одну и ту же позицию.
- Если вызовов не нашлось — искать шире: строка может собираться в две стадии (сначала
  `.Translate()`/чтение поля без аргументов, `.Formatted(...)` — отдельным вызовом в другом
  месте кода), либо ключ/путь формируется динамически. В этом случае честно сказать, что
  прямого вызова не нашлось, и объяснить, что удалось выяснить.

## Шаг 2: сопоставить плейсхолдер с аргументом вызова

**Сначала — обязательный разбор текста.** Возьми точный текст плейсхолдера из вопроса
переводчика (всё, что между `{` и `}`) и процитируй его дословно в ответе. Затем выполни
команду (замени на точный текст плейсхолдера):

```
python tools/parse_placeholder.py "точный текст плейсхолдера"
```

Скрипт детерминированно разберёт текст на `N`/`ИМЯ`, подсимвол и аргументы — в том числе
вложенные конструкции на любую глубину. Используй именно этот результат, а не собственный
разбор текста «на глаз» — на вложенности легко ошибиться вручную. Полное описание правил
разбора (на случай, если нужно проверить вывод скрипта, или он недоступен) —
[placeholder-syntax.md](placeholder-syntax.md).

Если скрипт по каким-то причинам недоступен — разбери текст вручную по **первому** символу
`_`: часть до него (или весь текст, если `_` нет) — это `N`/`ИМЯ`, используется ниже; часть
после первого `_` (если он есть) — подсимвол, используется в шаге 4. Наличие или отсутствие
подсимвола определяется **только** этим разбором точного текста вопроса — никогда не бери его
по сходству с примерами в документах или по «интуиции».

- `{N}` (число) → (N+1)-й аргумент вызова **по порядку в списке аргументов**, считая
  вообще все аргументы подряд — в том числе те, у которых есть `.Named(...)`. Так, в
  `"Key".Translate(a.Named("PAWN"), b)` плейсхолдер `{0}` — это `a` (тот же объект, что и
  `{PAWN}`), а `{1}` — это `b`.
- `{ИМЯ}` (не число) → аргумент, у которого `.Named("ИМЯ")`.

## Шаг 3: определить тип аргумента

По объявлению переменной/параметра в месте вызова определить C#-тип найденного аргумента —
это и есть ответ на вопрос "какие значения могут сюда попасть". Там, где тип абстрактный
(`Pawn`, `Thing`), уточнить по контексту метода, какие именно сущности туда реально
приходят (проверки, откуда берётся переменная и т.д.).

- Если аргумент — параметр метода, а не значение, созданное на месте: грепом по имени
  метода найти все места, откуда его вызывают (caller'ы) — там часто виден более
  конкретный смысл переменной, а разные вызовы могут передавать разные сущности.
- Если тип по-прежнему абстрактный и завязан на конкретный компонент
  (`CompXxx`/`CompProperties_Xxx`), поискать в `.Data/<DLC>/Defs/**`, у каких дефов этот
  комп указан в `<comps>` — так получается конкретный (исчерпывающий) список
  пешек/предметов, которые реально могут оказаться на месте плейсхолдера.

## Шаг 4: разобрать подсимвол, если он найден на шаге 2

Используй ровно тот результат разбора текста плейсхолдера, что был получен на шаге 2 —
не проверяй заново «на глаз» и не решай по сходству с примерами. Если разбор шага 2 дал
подсимвол — свериться с `python tools/subsymbols.py <Тип>` (предпочтительно, генерируется из
актуального кода игры) или с [grammar-symbols.md](grammar-symbols.md), что именно этот
подсимвол подставляет для данного типа.

## Шаг 5: проверить, не рекурсивно ли разрешение

Если подсимвол сам оказывается обращением к другому Keyed-ключу (пример — `PAWN_possessive`
в [keyed-strings.md](keyed-strings.md), который через `GenderUtility.GetPossessive` уходит
в `Prohis`/`Proits`/`Proher`) — повторить шаги 1–4 уже для этого ключа.

## Шаг 6: указать источник в ответе

Отвечать со ссылкой на источник (файл:строка вызова), а не только выводом — это позволяет
проверить ответ и не полагаться на догадку по имени ключа/поля/комментарию.

Примеры ниже показывают алгоритм на конкретных строках из прошлых вопросов. Для нового
вопроса путь к файлу, строку вызова и тип аргумента нужно найти заново тем же алгоритмом —
нельзя переносить их из примера в ответ на другой ключ/поле.

## Пример 1: Keyed-ключ

Ключ `FloatMenuContainmentRequires` в `Anomaly/Keyed/FloatMenu.xml`:

```xml
<!-- EN: {0_label} requires -->
<FloatMenuContainmentRequires>{0_label} требует:</FloatMenuContainmentRequires>
```

1. Грep по `.Decompiled` находит единственное место вызова —
   `FloatMenuOptionProvider_CarryingPawn.cs`:
   ```csharp
   "FloatMenuContainmentRequires".Translate(carriedPawn).ToLower()
   ```
2. `{0}` → первый (и единственный) аргумент вызова — `carriedPawn`.
3. Тип `carriedPawn` в сигнатуре метода — `Pawn`: перенесённое/захваченное существо,
   которое пытаются поместить в место изоляции.
4. `_label` — подсимвол `label` для `Pawn`: отображаемое имя/название пауна.

Итог: `{0_label}` — label существа (`Pawn`), которое переносит выделенный колонист и
пытается поместить в контейнер/платформу для изоляции.

## Пример 2: поле дефа (DefInjected)

Путь инъекции `DuplicateSickness.comps.HediffComp_MessageAboveSeverity.message` в
`Anomaly/DefInjected/HediffDef/Hediffs_Global_Misc.xml`:

```xml
<!-- EN: {0_nameDef} is now suffering from duplicate sickness. -->
<DuplicateSickness.comps.HediffComp_MessageAboveSeverity.message>{0_nameDef} недомогает из-за дупликации.</DuplicateSickness.comps.HediffComp_MessageAboveSeverity.message>
```

1. По пути инъекции ([def-injected.md](def-injected.md)) поле `message` относится к
   `HediffCompProperties_MessageAboveSeverity`. Поиск в `.Decompiled` показывает, где оно
   читается — `HediffComp_MessageAboveSeverity.CompPostTickInterval`:
   ```csharp
   Messages.Message(Props.message.Formatted(base.Pawn), base.Pawn, Props.messageType);
   ```
2. `{0}` → первый аргумент `.Formatted(...)` — `base.Pawn`.
3. Тип — `Pawn`: носитель хеддифа `DuplicateSickness` (дупликат/оригинал), у которого
   тяжесть состояния превысила порог `Props.severity`.
4. `_nameDef` — подсимвол `nameDef` для `Pawn`: имя пауна с определённым артиклем/без
   (см. `tools/subsymbols.py Pawn`).

Итог: тот же механизм (`.Formatted`), что и у Keyed-строк — источником строки было поле
дефа, а не ключ `Keyed`, но разрешение плейсхолдера идёт идентично.
